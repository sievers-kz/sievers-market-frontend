# Вход, регистрация, подтверждение почты

- **Маршруты:** `/login`, `/register` (шаги 1-2: данные аккаунта и код из письма), `/forgot-password` (этап 2). Онбординг после регистрации (кто вы, ИИН/БИН) описан в `docs/pages/onboarding.md`.
- **Доступ:** только для неавторизованных. Авторизованного пользователя с `/login` и `/register` перенаправляй: с ролью на `/`, без роли на `/onboarding`.
- **Макет:** Figma «AGROW», страница 1. Регистрация: `593:2` (шаг 1), `594:65` (шаг 2, код). Вход: только мобильный фрейм `756:497` (в файле `753:212`). Десктопного макета входа **нет**: сделай его по образцу карточки регистрации (одна белая карточка по центру, поля, кнопка). Макеты это **визуальный ориентир**, размеры подгоняй под сетку 8pt и токены.
- **Рендер:** страницы это Server Components с клиентским компонентом формы внутри (`"use client"` только у формы). Авторизацию страница проверяет на сервере через `getCurrentUser()`.

## Объём работ

### Этап 1 (делаем сейчас)
1. `/login`: вход по почте и паролю.
2. `/register`, шаг 1: почта, пароль, повтор пароля, два согласия, кнопка «Зарегистрироваться».
3. `/register`, шаг 2: ввод кода из письма, кнопка «Подтвердить», «Отправить код ещё раз».
4. `getCurrentUser()` в `lib/api/auth` (union по `role`) и перенаправления после входа и подтверждения.

### Этап 2 (после этапа 1, макета пока нет)
Восстановление пароля: `/forgot-password` (почта, `requestForgotPassword`), затем ввод кода и нового пароля (`resetUserPassword`). Ссылка «Забыли пароль?» в форме входа с этапа 1 уже должна вести на `/forgot-password` (страница-заглушка допустима).

## Вход (`/login`)
Поля: почта, пароль (кнопка «показать пароль»), ссылка «Забыли пароль?», кнопка «Войти», ссылка «Нет аккаунта? Зарегистрироваться» (на `/register`). Заголовок и подзаголовок из мобильного макета: «Вход в Sievers Market», «Чтобы связываться с продавцами и размещать объявления».

После успешного `loginUser`:
1. вызвать `getCurrentUser()`;
2. роль `customer` или `vendor` → перейти на адрес из `?next=` (только относительный путь на нашем сайте, иначе игнорировать) или на `/`;
3. роли нет → на `/onboarding`.

## Регистрация, шаг 1 (`/register`)
Поля по макету `593:2`: «Email», «Пароль», «Повтор пароля», чекбокс «Я соглашаюсь на получение информационных сообщений» (необязательный), чекбокс «Я соглашаюсь на обработку персональных данных в соответствии с политикой конфиденциальности и пользовательским соглашением» (обязательный), кнопка «Зарегистрироваться». Ссылки на политику и соглашение пока ведут на заглушки.

`createNewUser` получает только `email` и `raw_password`. Повтор пароля и оба согласия проверяются **только на клиенте** и в запрос не уходят.

После успеха (200) показать шаг 2 в той же странице. Почту держи в состоянии клиентского компонента формы (или в Zustand-сторе только для UI), **не** в URL и не в `localStorage`. После перезагрузки страницы пользователь снова на шаге 1; это нормально, см. «Расхождения».

## Регистрация, шаг 2: код (`/register`)
Заголовок «Подтвердите электронную почту», шесть ячеек для цифр (по макету `594:65`), кнопка «Подтвердить». Поведение ввода: вставка всего кода из буфера заполняет все ячейки, Backspace возвращает на предыдущую ячейку, `autocomplete="one-time-code"`, `inputmode="numeric"`.

Кнопка «Отправить код ещё раз» (`resendConfirmationCode`) после нажатия блокируется на время ожидания (см. «Расхождения», пока константа 60 секунд). При 429 `otp_cooldown_error` показать сообщение сервера.

После успешного `confirmAccount` бэкенд выставляет httpOnly-cookie сессии, то есть пользователь уже вошёл. Дальше: `getCurrentUser()` → роли нет → `/onboarding`. Тело ответа **не читать** (в нём для веб-клиента токенов быть не должно).

## Данные (операции API)
| Что | operationId | Примечание |
|---|---|---|
| Регистрация | `createNewUser` | тело `{ email, raw_password }` |
| Подтверждение | `confirmAccount` | тело `{ email, confirm_code }`; ставит cookie |
| Повторная отправка кода | `resendConfirmationCode` | тело `{ email }` |
| Вход | `loginUser` | тело `{ email, raw_password }`; ставит cookie |
| Кто я | `getMe` | union по `role`: `customer`, `vendor`, нет роли |
| Выход | `logoutUser` | понадобится в шапке и кабинете; сделать функцию сразу |
| Восстановление (этап 2) | `requestForgotPassword`, `resetUserPassword` | |

Функции кладём в `src/lib/api/auth.ts`, имена по `operationId`. Единая `getCurrentUser()` вызывает `getMe` и возвращает размеченный union; на 401 возвращает `null`, а не бросает исключение. Single-flight refresh на 401 уже есть в `apiFetch`.

## Валидация (Zod повторяет DTO)
- Почта: обязательна, формат email (`CreateAccountRequest.email`).
- Пароль: обязателен. Других ограничений в OpenAPI **нет**, не придумывай длину и состав, правила проверяет сервер (см. «Расхождения»).
- Повтор пароля: совпадает с паролем (только клиент).
- Согласие на обработку данных: обязательно (только клиент).
- Код: непустая строка из цифр; длину 6 берём из макета (в OpenAPI это просто `string`).
- Вход: почта и пароль обязательны, остальное решает сервер. На входе правила пароля не проверяй.

## Ошибки (`applyApiErrorToForm`, `byErrorCode`)
| Где | Ответ | Что показать |
|---|---|---|
| регистрация | 409 `account_already_exists_error` | под полем «Email» |
| регистрация | 400 `compromised_password_error` | под полем «Пароль» |
| регистрация | 422 `email_required_error`, `invalid_email_format_error` | под «Email» |
| регистрация | 422 `password_required_error`, `invalid_password_error` | под «Пароль» |
| подтверждение | 400 `invalid_otp_code_error` | под ячейками кода, поля очистить, фокус на первую |
| повторная отправка | 429 `otp_cooldown_error` | сообщением формы |
| вход | 401 `invalid_login_credentials_error` | **сообщением формы** («Неправильный email или пароль»), без указания поля |
| любая | 422 `{ detail: [{ loc, msg }] }` | по полям через `fieldErrors` |
| любая | 5xx, сеть, 503 | общее сообщение формы «Что-то пошло не так, попробуйте позже» |

Ошибки без поля показывай сообщением формы. Тексты `message` с сервера на русском, их можно показывать как есть.

Коды ошибок сейчас берутся из примеров в OpenAPI-документе проекта, в сгенерированном `schema.d.ts` их **нет** (ответы ошибок типизированы как `unknown`). Названия кодов держи в одном месте (`src/lib/api/error-codes.ts`), чтобы при расхождении поправить в одном файле.

## Состояния
- Кнопки отправки блокируются на время запроса, внутри индикатор загрузки; двойная отправка невозможна.
- `loading.tsx` для `/login` и `/register` не нужен (страницы статичные), `error.tsx` нужен.
- Доступность: у полей есть `label`, ошибки связаны через `aria-describedby`, фокус на первом поле с ошибкой, Enter отправляет форму.

## Расхождения и вопросы (не придумывать, описать в PR)
1. **Правила пароля** в OpenAPI не описаны (нет минимальной длины, состава). Нужно уточнить в бэкенде и дописать в Zod, пока только «обязателен».
2. **Длина кода**: макет показывает 6 цифр, в OpenAPI длины нет. Уточнить.
3. **Время ожидания повторной отправки** кода в OpenAPI нет. Пока константа 60 секунд, заменить на значение бэкенда.
4. **Вход с неподтверждённой почтой**: поведение неизвестно (отдаёт ли `loginUser` ошибку и какую, можно ли получить код заново). Проверить в Swagger на стенде до реализации; если нужен отдельный код ошибки, добавить в «Ошибки».
5. **Перезагрузка на шаге 2** теряет почту. Сохранять её в `sessionStorage` не хотим (лишнее хранилище в браузере). Если это станет проблемой, вариант: вход на `/login` для неподтверждённого аккаунта должен вести на шаг 2 (зависит от пункта 4).
6. **Согласия** (рассылка и обработка данных) в API не передаются. Если их нужно хранить, это задача бэкенда.
7. **Десктопного макета входа нет**, делаем по образцу регистрации; сверить с автором макета, когда он появится.
8. **Верхняя шапка в макете** показывает имя пользователя (`Мейржан Бисенов`) уже на экране регистрации, это артефакт макета. На страницах входа и регистрации шапка без блока пользователя (кнопки «Регистрация» и «Вход» по макету `739:9` или без них).
