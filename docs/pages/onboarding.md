# Онбординг после регистрации

- **Маршрут:** `/onboarding` (три шага внутри одной страницы: «Кто вы?», «ИИН/БИН», «Это ваша организация?»).
- **Доступ:** только авторизованный пользователь **без роли** (`getCurrentUser()` вернул «нет роли»). Неавторизованного отправь на `/login`, пользователя с ролью `customer` или `vendor` на `/`.
- **Макет:** Figma «AGROW», страница 1: шаг 3 `594:121` («Кто вы?»), шаг 4 `594:186` («Введите ИИН/БИН»), шаг 5 `594:242` («Это ваша организация?»). Номера шагов 1-2 относятся к регистрации (`docs/pages/auth.md`), сквозная нумерация в макете: 1 регистрация, 2 код, 3 кто вы, 4 ИИН/БИН, 5 подтверждение. Макет это **визуальный ориентир**, размеры подгоняй под сетку 8pt и токены. Кадры шагов 3-5 при подготовке спецификации смотрели только по названиям слоёв (лимит Figma), перед версткой открой их в Figma.
- **Рендер:** Server Component проверяет доступ через `getCurrentUser()`, клиентский компонент ведёт шаги.

## Объём работ
1. Шаг «Кто вы?»: выбор «Я покупатель» / «Я продавец».
2. Ветка покупателя: имя и фамилия → `createCustomer` → на `/`.
3. Ветка продавца: ввод ИИН/БИН и проверка → подтверждение организации → `createVendor` → на `/`.
4. Выход из онбординга нельзя «пропустить»: пока роли нет, любые страницы, требующие роль (создание объявления, кабинет), ведут сюда.

## Шаг «Кто вы?»
Две плитки в один ряд (два столбца): «Я покупатель» и «Я продавец». Плитки сделаны как радиокнопки (`input type="radio"` в группе с подписью), оформленные в виде небольших прямоугольных карточек: клавиатура и скринридер работают как у обычных радио. Не больше одного выбора, пользователя не перегружаем. Выбор можно менять до отправки. Состояние шага (выбранная роль, введённые данные) хранится в клиентском компоненте.

## Ветка покупателя
Поля `last_name` и `first_name` (оба обязательны, см. `CreateCustomerRequest`). Отчество в этом запросе не передаётся. Макета этой формы в файле нет: сделай форму в стиле карточки (две строки полей, кнопка «Продолжить»). Успех → `/`.

## Ветка продавца
Четыре шага внутри страницы (решение владельца продукта, 5 ноября).

**1. Тип.** Две плитки в один ряд (два столбца, в том числе на мобильном): «Физическое лицо» и «Юридическое лицо». Без подвыбора формы (ИП, ТОО, АО и т. д. пользователю не показываем).

**2. Номер.** Поле зависит от типа: физлицо вводит **ИИН**, юрлицо **БИН** (по 12 цифр). Кнопка «Проверить»; пока идёт запрос в КГД (через `verifyTaxpayer`), показывай индикатор загрузки, блок не прыгает.

**3. «Это ваша организация?»** Таблица данных из ответа проверки: наименование (`legal_name`), номер (`tax_id`) и остальное, что вернул `verifyTaxpayer`. Кнопки «Да» и «Нет». «Нет» возвращает на ввод номера.

**4. Недостающие поля.** Пользователь вводит сам, без сторонних библиотек и подсказок адресов: «Юридический адрес» (`legal_address`), «Фамилия» и «Имя» контактного лица (`contact_last_name`, `contact_first_name`). Кнопка «Создать» вызывает `createVendor`, успех → `/`. Контрольную цифру номера проверяет только `createVendor` (на фронтенде в Zod лишь 12 цифр): при 422 `invalid_tax_number_error` пользователь возвращается на ввод номера, ошибка показана под полем номера.

**Соответствие типа и `legal_form`** (временное, пока бэкенд не упростил enum, backend#213): физлицо → `IE`, юрлицо → `LLP`. Для проверки в КГД этого достаточно (бэкенд различает только `IP` и `UL`). `legal_name` и `legal_form` в `createVendor` передавай из результата проверки.

`createVendor` требует: `contact_last_name`, `contact_first_name`, `legal_name`, `legal_address`, `tax_id`, `legal_form`.

## Данные (операции API)
| Что | operationId | Примечание |
|---|---|---|
| Кто я | `getMe` | через `getCurrentUser()` |
| Профиль покупателя | `createCustomer` | `{ last_name, first_name }` |
| Проверка налогоплательщика | `verifyTaxpayer` | путь `tax_id`, query `legal_form`; ответ `{ tax_id, legal_name, legal_form, is_liquidation }` |
| Профиль продавца | `createVendor` | см. выше |

Функции кладём в `src/lib/api/customer.ts` и `src/lib/api/vendor.ts`. После успешного создания профиля заново вызови `getCurrentUser()` (роль изменилась), не угадывай роль по ответу создания.

## Валидация (Zod повторяет DTO)
- `last_name`, `first_name`: обязательные строки. Других ограничений в OpenAPI нет.
- `tax_id`: строка из 12 цифр (ИИН и БИН в Казахстане по 12 цифр; в OpenAPI это просто `string`, длину берём из предметной области, проверить на стенде).
- `legal_form`: в API enum `IE`, `LLP`, `JSC`, `FARM`; на фронтенде временно используются только `IE` (физлицо) и `LLP` (юрлицо), см. выше.
- `legal_address`, `contact_last_name`, `contact_first_name`: обязательные строки.

## Ошибки
| Где | Ответ | Что показать |
|---|---|---|
| проверка | 404 `taxpayer_not_found_error` | под полем номера |
| проверка и создание | 400 `taxpayer_on_liquidation_error` | под полем номера, на шаге «Это ваша организация?» сообщением формы |
| создание продавца | 409 `vendor_already_exists_error` | сообщением формы |
| создание продавца | 422 `invalid_tax_number_error` (только при создании, при проверке не приходит) | возврат на ввод номера, под полем номера |
| создание покупателя | 422 `fullname_required_error`, `invalid_fullname_format_error` | под полем из `metadata.field` (backend PR #214); нет `metadata.field` или такого поля в форме: сообщением формы |
| создание продавца | 422 `contact_fullname_required_error`, `contact_fullname_format_error` | под полем из `metadata.field`; нет `metadata.field` или такого поля в форме: сообщением формы |
| любая | 401 | единый обработчик: сессия истекла → `/login?next=/onboarding` |
| любая | 422 `{ detail: [...] }`, 5xx, сеть | по полям или общим сообщением формы |

Ошибки без поля показывай сообщением формы. Коды держи в `src/lib/api/error-codes.ts`.

## Состояния
Кнопки блокируются на время запроса; проверка ИИН/БИН может занять время (внешний реестр), покажи индикатор. `error.tsx` для маршрута обязателен.

## Расхождения и вопросы (не придумывать, описать в PR)
Расхождения бэкенда ведём в Issues `sievers-kz/sievers-market-backend` (проверь дубли перед новым).
1. **`legal_address` и ФИО контактного лица**: решено, продавец вводит их сам на шаге 4 (backend#207: откуда адрес берётся в идеале, остаётся вопросом).
2. **Тип налогоплательщика**: на фронтенде два значения (физлицо/юрлицо), в API четыре (`legal_form`). Временное соответствие описано выше, упрощение enum: backend#213.
3. **Макета формы покупателя** нет (см. выше), шага 4 продавца и плиток «физлицо/юрлицо» в макете тоже может не быть. Делай по описанию, как карточку стиля регистрации.
4. **`/me` без роли**: реальный ответ `role: null`, в `schema.d.ts` стоит `"None"`. `getCurrentUser()` принимает оба значения (backend#204).
5. **`legal_name` в запросе `createVendor`** игнорируется: бэкенд берёт название и форму из результата проверки, а не из тела (backend#207).
