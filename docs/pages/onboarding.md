# Онбординг после регистрации

- **Маршрут:** `/onboarding` (три шага внутри одной страницы: «Кто вы?», «ИИН/БИН», «Это ваша организация?»).
- **Доступ:** только авторизованный пользователь **без роли** (`getCurrentUser()` вернул «нет роли»). Неавторизованного отправь на `/login`, пользователя с ролью `customer` или `vendor` на `/`.
- **Макет:** Figma «AGROW», страница 1: шаг 3 `594:121` («Кто вы?»), шаг 4 `594:186` («Введите ИИН/БИН»), шаг 5 `594:242` («Это ваша организация?»). Номера шагов 1-2 относятся к регистрации (`docs/pages/auth.md`), сквозная нумерация в макете: 1 регистрация, 2 код, 3 кто вы, 4 ИИН/БИН, 5 подтверждение. Макет это **визуальный ориентир**, размеры подгоняй под сетку 8pt и токены. Кадры шагов 3-5 при подготовке спецификации смотрели только по названиям слоёв (лимит Figma), перед версткой открой их в Figma.
- **Рендер:** Server Component проверяет доступ через `getCurrentUser()`, клиентский компонент ведёт шаги.

## Объём работ
1. Шаг «Кто вы?»: выбор «Я покупатель» / «Я продавец».
2. Ветка покупателя: имя и фамилия → `createCustomer` → на `/`.
3. Ветка продавца: ввод ИИН/БИН и проверка → подтверждение организации → `createVendor` → на `/`.
4. Выход из онбординга нельзя «пропустить»: пока роли нет, любые страницы, требующие роль (создание объявления, кабинет), ведут сюда.

## Шаг «Кто вы?»
Две карточки: «Я покупатель» и «Я продавец». Выбор можно менять до отправки. Состояние шага (выбранная роль, введённые данные) хранится в клиентском компоненте.

## Ветка покупателя
Поля `last_name` и `first_name` (оба обязательны, см. `CreateCustomerRequest`). Отчество в этом запросе не передаётся. Макета этой формы в файле нет: сделай форму в стиле карточки (две строки полей, кнопка «Продолжить»). Успех → `/`.

## Ветка продавца
**Шаг «Введите ИИН/БИН».** Переключатель «Физическое лицо» / «Юридическое лицо», поле номера (подпись «ИИН» или «БИН», 12 цифр), кнопка «Проверить». Для юридического лица ещё нужен «Тип юридического лица» (`legal_form`), см. «Расхождения».
Проверка: `verifyTaxpayer(tax_id, legal_form)`.

**Шаг «Это ваша организация?».** Показывает ответ проверки: наименование (`legal_name`), форму (`legal_form`), номер (`tax_id`). Кнопка «Подтвердить» вызывает `createVendor`, кнопка «Назад» возвращает на ввод номера. Успех → `/`.

`createVendor` требует: `contact_last_name`, `contact_first_name`, `legal_name`, `legal_address`, `tax_id`, `legal_form`. Часть полей приходит из проверки, остальное вводит пользователь (см. «Расхождения»).

## Данные (операции API)
| Что | operationId | Примечание |
|---|---|---|
| Кто я | `getMe` | через `getCurrentUser()` |
| Профиль покупателя | `createCustomer` | `{ last_name, first_name }` |
| Проверка налогоплательщика | `verifyTaxpayer` | путь `tax_id`, query `legal_form`; ответ `{ tax_id, legal_name, legal_form, is_liquidation }` |
| Профиль продавца | `createVendor` | см. выше |

Функции кладём в `src/lib/api/customer.ts` и `src/lib/api/vendor.ts`. После успешного создания профиля заново вызови `getCurrentUser()` (роль изменилась), не угадывай роль по ответу создания.

## Валидация (Zod повторяет DTO)
- `last_name`, `first_name`: обязательные строки. Других ограничений в OpenAPI нет.
- `tax_id`: строка из 12 цифр (ИИН и БИН в Казахстане по 12 цифр; в OpenAPI это просто `string`, длину берём из макета и предметной области, проверить на стенде).
- `legal_form`: одно из `IE`, `LLP`, `JSC`, `FARM` (enum `LegalForm`). Подписи в интерфейсе на русском (ИП, ТОО, АО, КХ/ФХ), согласовать с автором.

## Ошибки
| Где | Ответ | Что показать |
|---|---|---|
| проверка | 404 `taxpayer_not_found_error` | под полем номера |
| проверка и создание | 400 `taxpayer_on_liquidation_error` | под полем номера, на шаге «Это ваша организация?» сообщением формы |
| создание продавца | 409 `vendor_already_exists_error` | сообщением формы |
| создание покупателя | 422 `fullname_required_error`, `invalid_fullname_format_error` | под соответствующим полем |
| любая | 401 | единый обработчик: сессия истекла → `/login?next=/onboarding` |
| любая | 422 `{ detail: [...] }`, 5xx, сеть | по полям или общим сообщением формы |

Ошибки без поля показывай сообщением формы. Коды держи в `src/lib/api/error-codes.ts`.

## Состояния
Кнопки блокируются на время запроса; проверка ИИН/БИН может занять время (внешний реестр), покажи индикатор. `error.tsx` для маршрута обязателен.

## Расхождения и вопросы (не придумывать, описать в PR)
Вопросы 1-3 ведёт бэкенд-Issue #207 (`feat(vendor)`: откуда берутся `legal_address` и ФИО контактного лица), загляни в него до работы.
1. **`legal_address`**: `createVendor` требует юридический адрес, а ответ `verifyTaxpayer` его не содержит. В старых кадрах (например, `339:2`) есть поле «Юридический адрес». Нужно решить: вводит пользователь или бэкенд должен вернуть адрес из реестра. Пока не придумывай, остановись и опиши.
2. **ФИО контактного лица** (`contact_last_name`, `contact_first_name`) продавец вводит где-то, но в кадрах 3-5 такого поля нет. Нужен макет или решение: добавить поля на шаг «ИИН/БИН» или на отдельный шаг.
3. **Физическое лицо и `legal_form`**: переключатель «Физическое лицо» / «Юридическое лицо» не совпадает с enum (`IE`, `LLP`, `JSC`, `FARM`). Как «физическое лицо» ложится на enum (скорее всего `IE` для ИП), и существует ли «частный продавец» без ИП (в других кадрах Figma он есть), решает владелец продукта. API частного продавца не знает.
4. **Макет формы покупателя** отсутствует (см. выше).
5. **`/me` без роли**: реальный ответ `role: null`, в `schema.d.ts` стоит `"None"`. `getCurrentUser()` уже принимает оба значения (backend#204).
6. **Бэкенд-код `legal_name` в запросе игнорируется**: `createVendor` берёт название и форму из результата проверки, а не из тела запроса (backend#207).
