# Переход на модель организаций (ломающие изменения бэкенда)

**Прочитай целиком перед любой работой.** Бэкенд (PR №226, №227) убрал роли `customer` и `vendor`, онбординг и вход через `getMe`. Теперь есть один аккаунт — **покупатель** (customer), и у него может быть несколько **организаций**. Объявление подаётся от имени организации. Фронтенд собран под старую модель, поэтому после `npm run gen:api` `typecheck` упадёт сразу в нескольких местах. Это ожидаемо: часть кода нужно **удалить**, а не чинить.

Работа делится на три PR, строго по порядку. В каждом PR сначала прочитай `docs/STATUS.md`, в конце обнови его. Отдельный экран «Мои организации» описан в `docs/pages/organizations.md`.

| PR | Ветка | Тема |
|---|---|---|
| 1 | `feature/customer-model` | Основа: `getCurrentUser()` на `GET /customer/me`, удаление ролей и онбординга, правки экранов под потерянные поля |
| 2 | `feature/organizations` | Экран «Мои организации» (`docs/pages/organizations.md`) |
| 3 | `feature/listing-organization` | Выбор организации в форме объявления и доступ к `/listings/new` |

## Что изменилось в API

Источник правды — `schema.d.ts` после `npm run gen:api`. Ниже то, что нужно знать заранее.

**Исчезло** (не вызывать, не оставлять в коде): `getMe` (`GET /iam/me`), `createCustomer`, `verifyTaxpayer`, `createVendor`, `getMeListings`, весь контекст vendor. Роли `customer` / `vendor` и значение `role: null` больше не существуют.

**Появилось:**
| operationId | Метод и путь | Назначение |
|---|---|---|
| `getCustomerMe` | `GET /customer/me` | Профиль текущего аккаунта. Если профиля нет, бэкенд создаёт его сам при первом обращении |
| `changeCustomerFullname` | `PATCH /customer/fullname/change` | Смена ФИО (в этих PR не используется) |
| `createOrganization` | `POST /customer/organization` | Добавить организацию по `tax_id` и `kind`; ответ **201** `{ id, registry_status: "pending" }` |
| `getOrganizations` | `GET /customer/organizations` | Список организаций пользователя в порядке добавления (`OrganizationListResponse[]`) |
| `getOrganization` | `GET /customer/organization/{organization_id}` | Полные данные, используется для опроса статуса |
| `deleteOrganization` | `DELETE /customer/organization/{organization_id}` | **204**; только для `pending` и `not_found` |

**Изменилось:**
- `CustomerMeResponse`: `id`, `email`, `password_changed_at`, `last_name`, `first_name`, `patronymic` (все три ФИО могут быть `null`). Поля `role` и `profile` нет.
- `createListing`: добавилось обязательное `organization_id` (uuid).
- `ListingDetailResponse`: **исчезли `display_owner_name` и `contact_phone`**; `owner_id` теперь это id **организации**, не пользователя.
- `ListingCardResponse` (каталог): **исчезло `display_owner_name`**.
- Регистрация больше не требует имени: имя не запрашивается нигде при регистрации.

**Статусы организации** (`registry_status`):
- `pending` — проверка в реестре ещё идёт (обычно секунды; если реестр недоступен, бэкенд повторяет проверку до пяти раз с нарастающей паузой, это около 15 минут; статус всё это время остаётся `pending`);
- `verified` — организация подтверждена, **только от неё можно подавать объявления**;
- `not_found` — в реестре нет действующего налогоплательщика с таким номером и типом `kind` (номер неверен, тип не совпал или организация ликвидирована).

`kind`: `individual` — ИП (вводится ИИН), `company` — юридическое лицо (вводится БИН). `tax_id` всегда ровно 12 цифр (`^\d{12}$`). Поле `is_ownership_verified` в интерфейсе **не используем** (проверки владения пока нет, всегда `false`).

**Коды ошибок** (кладутся в `src/lib/api/error-codes.ts`; `taxpayerNotFound`, `taxpayerOnLiquidation`, `vendorAlreadyExists`, `invalidTaxNumber`, `fullnameRequired`, `invalidFullnameFormat`, `contactFullnameRequired`, `contactFullnameFormat` удали, их больше нет):
| Код | Статус | Где |
|---|---|---|
| `organization_already_exists_error` | 409 | `createOrganization`: такой `tax_id` уже зарегистрирован |
| `organization_not_found_error` | 404 | `getOrganization`, `deleteOrganization`, `createListing` (чужая или несуществующая организация) |
| `organization_cannot_be_deleted` | 400 | `deleteOrganization` для `verified` |
| `organization_cannot_publish_error` | 403 | `createListing`, организация не `verified` |

В OpenAPI описаны не все статусы (нет 401 и других): ориентируйся на коды из таблицы и общий обработчик 401.

## PR 1. Основа (`feature/customer-model`)

Цель: проект собирается и работает на новой модели, без экрана организаций. Это самый «ломающий» PR, делай аккуратно и по шагам.

1. `npm run gen:api` (стенд обновлён). Убедись, что в `schema.d.ts` есть `getCustomerMe`, `getOrganizations` и нет `getMe`.
2. **`src/lib/api/auth.ts`:** удали `getMe` и тип union с ролями. `getCurrentUser()` вызывает `getCustomerMe` (`GET /api/v1/customer/me`, `cache: "no-store"`) и возвращает `CustomerMeResponse | null`; на 401 `null`, остальное пробрасывает. Тип `CurrentUser` теперь `CustomerMeResponse` (поправь использования). Комментарий про `role: null` / `"None"` (backend#204) удали.
3. **Удали файлы и код:** `src/lib/api/vendor.ts`, `createCustomer` из `src/lib/api/customer.ts` (в файле останется то, что понадобится в PR 2, пока можно оставить пустым или удалить файл и создать `organization.ts` в PR 2), экспорты удалённых функций из `src/lib/api/index.ts`. Каталог `src/components/onboarding/` целиком (**кроме `tile-radio-group.tsx`**: перенеси его в `src/components/common/`, он понадобится в PR 2), маршрут `src/app/(auth)/onboarding/`, `src/components/layout/no-role-actions.tsx`. Из `error-codes.ts` убери устаревшие коды, добавь новые (таблица выше).
4. **Переходы после входа и подтверждения почты:** `getPostAuthPath` больше не знает про онбординг: всегда `safeNextPath(next) ?? "/"`. Страницы `/login`, `/register`: авторизованного отправляй на `/` (раньше «с ролью на `/`, без роли на `/onboarding`»). Проверь `confirm-code-form.tsx`, `login-form.tsx`, `form-message.tsx`.
5. **Шапка** (`docs/pages/header.md`, обновлён): состояний два — гость и пользователь. Меню пользователя: строка с именем и почтой, «Выйти». Пункт «Мои организации» добавишь в PR 2, когда появится страница. Буква аватара и имя: см. `header.md`; `user-display.ts` переписать под `CustomerMeResponse` (ролей нет).
6. **`PostListingButton`:** гость → `/login?next=/listings/new`; авторизованный (и пока проверка идёт) → `/listings/new`. Поповер «станьте продавцом» **удалить**.
7. **`/listings/new` в этом PR:** `ListingCreateGate` теперь проверяет только вход (гостя на `/login?next=/listings/new`). Форма ждёт выбор организации из PR 3, поэтому для вошедшего пользователя временно показывай заглушку «Подача объявлений скоро будет доступна» (с пометкой `TODO` в коде, удаляется в PR 3). Чтобы проект собирался, `ListingCreateFlow` принимает обязательный проп `organizationId: string` и передаёт его в `createListing` как `organization_id`; из заглушки он пока не вызывается. Не переписывай форму больше, чем нужно для компиляции.
8. **Страница объявления** (`docs/pages/listing.md`, обновлён): карточка продавца и `ShowPhoneButton` **удаляются**, потому что данных для них больше нет (`display_owner_name`, `contact_phone`). Раскладку на телефоне поправь (порядок блоков без карточки продавца). Сам блок продавца вернём отдельной задачей, когда определимся с данными организации (backend#207), заглушек и «Продавец скрыт» не рисуй.
9. **Каталог:** из карточки (`listing-card.tsx`, плитка и список) убрать строку с названием продавца. Раскладку подогнать под сетку 8pt.
10. Обнови `docs/STATUS.md`: что сделано, удалённые решения (сессия, роли, онбординг, «тип продавца», поповер кнопки), известные ограничения.

Проверка: `typecheck`, `lint`, `build`. Прогони руками: регистрация → подтверждение → попадаешь на `/` с аватаром; вход; выход; `/listings/new` для гостя и вошедшего; каталог; страница объявления.

## PR 3. Организация в форме объявления (`feature/listing-organization`)

1. `/listings/new` для вошедшего: клиентский компонент запрашивает `getOrganizations()` (в браузере, чтобы работал refresh; на сервере токен не обновляется). Пока идёт запрос — скелетон.
2. **Нет ни одной организации** → вместо формы заглушка: «Чтобы подать объявление, добавьте организацию» и кнопка «Добавить организацию» (`/account/organizations`).
3. **Организации есть, но ни одна не `verified`** → вместо формы заглушка с учётом статусов: если есть `pending` — «Мы проверяем вашу организацию в реестре. Подавать объявления можно после подтверждения», если все `not_found` — «Организацию не удалось найти в реестре. Проверьте номер или добавьте другую»; кнопка «Мои организации».
4. **Есть хотя бы одна `verified`** → показывается форма (`docs/pages/listing-create.md`, раздел «Организация»).
5. Удали временную заглушку из PR 1.

## Открытые вопросы по дизайну (не придумывай — реализуй как описано, отличия опиши в PR)

Дизайн выбора организации в форме не утверждён (макет Figma «Frame 848» — ориентир, не финал). Поэтому:
- выбор организации делается **отдельным компонентом** `OrganizationSelect` (`src/components/listing-create/`), у которого нет привязки к месту в раскладке: его можно перенести или заменить карточками, не трогая остальное;
- форматирование опций (название, номер) и расположение блока описаны в `listing-create.md` как решение «по умолчанию»;
- в `organizations.md` формулировки типа организации и статусов — предложение, их можно менять правкой одного файла констант (`organization-labels.ts`), держи тексты там.

## Что не делаем

Основная («по умолчанию») организация, редактирование организации, `shop_name`, `logo_media_id`, контакты и адрес организации, проверка владения (`is_ownership_verified`), блок продавца на странице объявления, имя пользователя при регистрации и экран профиля (смена ФИО), «Мои объявления». Новые библиотеки без согласования не добавляем.

## Расхождения, которые нужно описать в PR, если встретишь
